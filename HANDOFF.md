## 3. Running

```bash
dune build
tests/run.sh                 # everything, incl. the fuzzer self-test
CC=clang tests/run.sh        # same with Clang
tests/fuzz/selftest.sh       # fuzzer self-tests only (parallel)
```

Fuzzer (`STARNITE` names the compiler, `FUZZ` the fuzz binary in scripts): `--count N --seed S`, `--shrink`, `--negative-only`, `--no-negative`, `--print --mutated --seed N`, `--reduce FILE` (with `--keeping TEXT`, `--rejected CODE`, `--keeping-match HEADER --arm HEAD`), `--keep DIR`. Also `--write DIR`, `--crash`, `--corruptions N`.
Do not rebuild `_build` while a background run uses its binaries; use `--build-dir` copies. Foreground `sleep` is blocked in this environment.

## 5. Remaining milestone 1

- The fuzzer oracle "compare each optional pass on and off" waits for the optional passes (later milestone).
- The stack-overflow handler (`runtime/stn_runtime.c`) decides by the faulting address against the stack limit read at start-up. Platform stack and guard bounds, or an explicit runtime check, were suggested in review and not done.
- `split_at_mut`, `Slice[T]`, `StrView`: views into a borrowed buffer; need the `local` mode of milestone 3 (section 10.5). `swap` covers the common case. The array search function is unspecified in the draft.
- E0205 and `Iter`/`Send`/`Abandon`/`Cont` need later milestones.
- Property, snapshot and doc tests belong to milestone 2.
- `Array[T, N]` is specified for milestone 5 only; nothing of it is built.

## 6. Known issues

- The interpreter's recursion limit is lower than C's: a 100k-deep recursion overflows in the interpreter (E0100 "nested too deeply") but runs in C. Differences of this kind are not fuzzed.
- Stack overflow in C is a trap through a `sigaltstack` SIGSEGV/SIGBUS handler (`runtime/stn_runtime.c`).
- `main` locally (before fetch) may be stale: always branch from `origin/main`.
- Other local branches (`lend-wip`, `speed-wip`, `wip/fuzz-negative`) are old experiments; `wip/fuzz-negative` is superseded by PR #8.
